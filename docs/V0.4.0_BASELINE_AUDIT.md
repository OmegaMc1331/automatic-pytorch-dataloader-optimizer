# APDO v0.4.0 Baseline Audit

- Baseline commit: `abda9af7154e691f2163897556610eba25f5928d`
- Baseline version: `0.3.0`
- Benchmark protocol: `3.0`
- Audit date: 2026-11-17

## Purpose

This audit records the measured and code-level behavior of APDO v0.3.0 before the
v0.4.0 timing, comparability, and stability work. It separates confirmed defects from
limitations and identifies which existing behavior must remain compatible.

## Confirmed timing findings

### P0-1: Iterator initialization is outside the measured startup

`_run_cycle()` performs `iter(loader)` before starting its startup timer. The measured
`startup_s` therefore includes only the first `next(iterator)` call.

A direct probe with 32 samples, batch size 4, and one worker measured the following:

| Configuration | Epoch | `iter(loader)` | First batch |
| --- | ---: | ---: | ---: |
| `num_workers=0` | 1 | 0.416 ms | 5.898 ms |
| `num_workers=1`, non-persistent | 1 | 20.843 ms | 2,347.797 ms |
| `num_workers=1`, persistent | 1 | 12.800 ms | 2,699.635 ms |

The first-batch cost dominates on Windows, but iterator construction is measurable and
must be reported independently. On platforms where iterator construction is more
expensive, excluding it would be misleading.

### P0-2: Sustained throughput can hide very large trial costs

APDO records sustained throughput and total elapsed time separately, but search and
validation rank configurations by throughput. With `epochs > 1`, the current
`sustained_throughput` excludes the entire first cycle and does not include epoch
transitions or shutdown.

Probe results for 96 samples processed over 3 epochs with batch size 4:

| Configuration | Current sustained throughput | Full trial wall | Total samples | Amortized throughput |
| --- | ---: | ---: | ---: | ---: |
| `num_workers=0` | 1,073.9 samples/s | 0.102 s | 96 | 939.4 samples/s |
| 1 worker, non-persistent | 1,032.0 samples/s | 7.464 s | 96 | 12.9 samples/s |
| 1 worker, persistent | 1,048.6 samples/s | 2.671 s | 96 | 35.9 samples/s |

The non-persistent configuration paid approximately 4.91 seconds of worker restart
overhead across epochs, yet its sustained value was within 4% of the others. A
sustained-only ranking can therefore recommend a configuration that takes roughly 6.8
times longer to execute the requested epochs on Windows. v0.4.0 must distinguish the
ranking metric explicitly and provide total-trial amortized throughput.

### P0-3: Worker shutdown is unmeasured

Worker shutdown is performed after `duration_s` is captured. `total_elapsed_s` is a
sum of startup, execution, construction, and training setup, not a measurement of the
actual trial lifetime. Loader destruction and worker teardown therefore do not appear
in any reported duration, although they affect user-visible cost.

For persistent workers, final teardown occurs when the loader is destroyed. For
non-persistent workers, each iterator is shut down at the end of its cycle. These two
costs have different meanings and need separate fields.

### P0-4: First-batch accounting is not consistent across epoch counts

For loader mode with one epoch, APDO subtracts the first batch samples from the
throughput numerator because the first batch acquisition occurs before the execution
timer starts. For multiple epochs, it drops the entire first cycle and retains the
first batch samples of subsequent cycles even though those batches were also acquired
before their execution timers started.

This does not affect training mode in the same way: the first training step is inside
the execution timer, so its samples and step time are both included. The training
first-batch path was inspected and is not a separate defect.

### P0-5: CUDA timing is host-submission timing, not device time

The current implementation synchronizes CUDA at cycle boundaries before capturing
wall duration. That is appropriate for including outstanding GPU work in the
end-to-end wall time, but it does not provide:

- a CUDA-event device-time measurement;
- separate host transfer submission time and device transfer time;
- per-step device time for detailed profiles;
- explicit identification of which reported fields use the CPU clock versus a CUDA
  event.

The baseline does not synchronize on every batch, which is correct. v0.4.0 must keep
that rule and make the clock semantics explicit.

A direct probe of 300 training steps demonstrated that host wall time and CUDA-event
time converge for a sufficiently large workload, but the current model does not expose
both measurements.

### P0-6: CPU and transfer resources are only partially represented

`EnvironmentInfo` records Python, PyTorch, CUDA runtime, GPU names, CPU count,
affinity count, RAM, and available memory. It does not record CPU model, physical
cores, or pin-memory support in one consolidated machine-readable hardware section.
`pin_memory` is only offered for CUDA devices, which is correct for the current
design, but the report needs an explicit resource summary and a clear statement that
pinned-memory behavior depends on the platform build.

## Confirmed comparability and reliability gaps

### P1-1: No batch comparability diagnostics

There is no structural batch signature, no sample fingerprint, no same-set comparison,
and no comparability policy attached to search or validation results. APDO cannot
currently state whether the measured configurations saw the same logical data.

### P1-2: No recommendation stability evaluation

There is no API or CLI path that runs the complete optimization process repeatedly
with independently derived execution seeds and summarizes selected-configuration
frequencies, validation outcomes, gains, fallbacks, or failures. A single search
success rate cannot be inferred from the existing round-level bootstrap intervals.

### P1-3: Reports lack timing and reliability sections

The schema-v3 JSON and static HTML reports expose aggregate throughput, startup,
latency, worker-transition, and validation data, but not lifecycle phase breakdowns,
CUDA device time, comparability evidence, selection-metric definitions, or
recommendation reliability.

### P1-4: Workloads do not deliberately separate startup-bound and compute-bound cases

The four existing workloads are in-memory loading, disk-backed loading, CPU-heavy
loading, and training. They are useful correctness and smoke-test workloads, but they
do not directly exercise the contrast between a loader dominated by worker startup
and a loader dominated by compute.

## Compatibility constraints confirmed by inspection

- `_run_cycle()` reuses one loader across all configured epochs of a trial.
- Persistent workers are reused by PyTorch inside that trial, but not across separate
  trials or configurations.
- Default epochs are 1 in loader mode and 3 in training mode.
- Search selection currently uses `summary.median_throughput`.
- Independent validation currently compares `PassMetrics.throughput` and requires at
  least two paired rounds.
- `training_step_factory` currently returns a callable that receives an already-moved
  batch; no device argument is currently part of its signature.
- APDO never starts training implicitly.
- The public API accepts dataset, existing DataLoader, or loader factory input.
- The current report protocol and metric protocol are version `3.0`.

## Required corrections and validation

### P0

1. Measure iterator construction and first-batch acquisition separately.
2. Keep the execution timer starting after first-batch acquisition; include the first
   training step when training mode is active.
3. Exclude the first loader batch from execution throughput unless it is processed
   inside the measured execution window.
4. Measure epoch transitions and worker/iterator shutdown separately.
5. Record full trial wall time and total-trial amortized throughput from actual samples
   processed.
6. Make the ranking metric explicit. Preserve historical sustained behavior as the
   documented default for v0.4.0 and add amortized selection.
7. Add standard and detailed timing profiles with explicit CPU/CUDA clock semantics and
   CUDA Events for device time.
8. Add tests using a controlled fake clock for lifecycle accounting and real CUDA
   validation for event timing where CUDA is available.
9. Reject invalid metrics, profiles, policies, and impossible lifecycle values.

### P1

1. Add structural signatures and optional user-provided sample fingerprints.
2. Compare same order, same sample set, different content, and unknown identity without
   storing raw batch data by default.
3. Add `off`, `warn`, and `strict` comparability policies with explicit gating rules.
4. Add repeated-run stability evaluation with independent seeds, partial-failure
   reporting, and machine-readable/static-HTML output.
5. Extend JSON/HTML reports with timing, comparability, reliability, and selection
   metadata.
6. Add startup-bound and compute-bound workloads; preserve the existing workloads.
7. Update examples and documentation so training steps do not perform redundant
   host-to-device transfers.
8. Add environment details needed to interpret pin-memory and CUDA results.

## Deliberate non-goals

- No architectural rewrite of the search/validation stages.
- No per-batch CUDA synchronization in the standard profile.
- No background daemon, web application, or external service dependency.
- No claim that local synthetic benchmark numbers generalize to real datasets.
- No silent change to existing defaults or to the meaning of existing report fields.
