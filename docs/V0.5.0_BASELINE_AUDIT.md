# APDO v0.5.0 Baseline Audit

This audit records the v0.4.1 behavior that motivated the v0.5.0 optimization and resource-awareness release. It was performed against the released `v0.4.1` tag (`484b320`) on the same Windows machine used for the v0.5.0 qualification.

The purpose of v0.5.0 is not to weaken the v0.4.1 statistical gate. Search, screening, budgets, cache hints, and profitability estimates remain advisory until fresh independent validation confirms a gain.

## Severity legend

- **High**: can waste substantial optimization time, mislead the recommendation, or make release evidence harder to audit.
- **Medium**: can mislead an operator or make a report internally inconsistent.
- **Low**: documentation, diagnostics, or presentation defect without a direct decision error.

## Findings

### P1-1: Search cost scaled with the full worker and flag grid

**Severity:** High

v0.4.1 evaluated a fixed grid of worker counts and loader flags. The search was deterministic and statistically safe, but every additional worker candidate paid warmup and measured rounds. On slower storage or expensive preprocessing, most of the optimization time could be spent on configurations that were never competitive.

v0.5.0 keeps grid search as the default and adds `search_strategy="adaptive"`. Adaptive search screens worker counts with fewer rounds, reduces the worker candidate set, refines one worker finalist, and records the stage decisions in `SearchTrace`. The selected candidate still passes the same independent validation gate.

Evidence: `tests/test_search.py` covers adaptive worker counts and trace fields. `tests/test_optimizer.py::test_optimize_adaptive_search_records_trace_and_budget` covers the end-to-end adaptive path.

Adaptive search is deterministic screening and refinement, not full successive-halving racing. Promotion and elimination statuses are represented in the search vocabulary, but the current optimizer records `screened`, `finalist`, `failed`, and `budget_skipped` outcomes. That limitation is documented rather than presented as a stronger algorithm.

### P1-2: Time budgets were not category-aware or reservation-aware

**Severity:** High

v0.4.1 had a deadline check, but it did not account for search, training finalists, validation, cleanup, and overhead separately, and it did not reserve capacity for the independent validation phase. A budget could therefore stop work without an explicit explanation of which phase was truncated or whether confirmation remained possible.

v0.5.0 introduces `BudgetController` with categorized phases and `estimate_validation_budget`. Validation capacity is reserved before the search consumes the remaining budget. If the reservation is insufficient, validation is skipped and the initial configuration is retained. Legacy tiny budgets still produce a safe baseline with `budget_exhausted=True` and a warning.

Evidence: `tests/test_budget.py` covers unlimited budgets, expiry, reservation, insufficient reservation, trial estimates, and validation budgets. `tests/test_optimizer.py` covers budget-truncated validation and the legacy tiny-budget path.

The budget is cooperative, not a hard process timeout. It is checked at measured round boundaries, so a single long trial can overrun the requested budget.

### P1-3: Repeated optimizations had no safe local reuse path

**Severity:** High

v0.4.1 repeated the full search on every invocation. Users who ran the same workload in the same environment paid the search cost again, with no opt-in mechanism to reuse a previous recommendation.

v0.5.0 adds an opt-in local JSON cache with `off`, `hint`, and `revalidate` policies. Entries contain a deterministic identity built from the package, protocol, source, settings, plan, and environment. Cache access is bounded, atomic, and tolerant of corrupt or stale entries. A cache hit can focus the search, but it never replaces fresh independent validation.

Evidence: `tests/test_cache.py` covers round-trip identity, stale protocol entries, corrupt entries, and safe clearing. `tests/test_optimizer.py` covers cache storage and reuse after a confirmed gain. `tests/test_cli.py` covers `apdo cache list` and `apdo cache clear --yes`.

The cache is local and opt-in. It is not a shared recommendation service and it does not make historical evidence current.

### P1-4: Optimization cost had no profitability estimate

**Severity:** High

v0.4.1 reported the optimization duration and the measured throughput change, but it did not estimate whether the saved time would repay the optimization cost over a realistic future horizon. A large relative gain on a short workload could still be a net loss.

v0.5.0 adds `ProfitabilityEstimate` for loader-only and end-to-end training scopes. It reports saved seconds per epoch, net savings, break-even epochs, conservative and optimistic bounds, and a status such as `profitable`, `not_profitable`, `uncertain`, `no_confirmed_gain`, `insufficient_data`, or `not_evaluated`. The estimate can be recomputed with `result.estimate_profitability(planned_epochs=..., planned_sessions=...)`.

Evidence: `tests/test_profitability.py` covers profitable, unconfirmed, missing-horizon, baseline, high-cost, and insufficient-data cases. `tests/test_report.py` covers the profitability report section.

Profitability estimates depend on the supplied horizon and observed throughput. They do not model workload drift, changing hardware, or non-linear training costs.

### P2-1: Resource diagnostics omitted effective CPU and cgroup constraints

**Severity:** Medium

v0.4.1 reported logical CPU count, affinity when available, memory, GPUs, and Torch thread count. It did not report the effective CPU count after cgroup limits, the multiprocessing start method, or cgroup memory and CPU limits. Worker search could therefore exceed a container's CPU allocation even when host affinity looked generous.

v0.5.0 reports `effective_cpu_count`, `multiprocessing_start_method`, `cgroup_memory_limit_bytes`, and `cgroup_cpu_limit`. `available_cpu_count()` now caps the host/affinity count by the cgroup CPU quota when that quota is readable. The environment payload and text/HTML environment table include the new fields.

Evidence: `tests/test_resources.py` covers environment collection and plausible cgroup limits. The six-workload v0.5.0 run records the new fields in every report.

Resource reporting remains advisory. The memory limit is sampled, not enforced by the operating system, and a worker can still fail after a successful memory sample.

### P2-2: Reports and CLI did not expose search, budget, profitability, or cache state

**Severity:** Medium

v0.4.1 reports exposed the search result, validation evidence, timing, and environment, but an operator could not see which search strategy ran, how much budget was consumed, whether a cache hint was used, or whether the optimization was expected to pay back.

v0.5.0 updates the report contract to schema 5 and protocol 5.0. Text, JSON, and HTML reports include search trace, budget, profitability, and cache sections. The CLI exposes `--search-strategy`, `--time-budget-s`, `--planned-epochs`, `--planned-sessions`, `--cache-policy`, `--cache-key`, and `--cache-dir` for benchmark and stability runs.

Evidence: `tests/test_report.py` covers schema 5, protocol fields, empty-section behavior, and v0.5 report sections. `tests/test_cli.py` covers the new flags and safe cache commands. `tests/test_package.py` covers the new public exports.

### P2-3: Adaptive decisions were not visible in a stable trace

**Severity:** Medium

v0.4.1 had no search trace because it had one search strategy. A v0.5.0 adaptive run needs to show which candidates were screened, which failed, which were skipped by budget, and which candidate became the finalist.

v0.5.0 adds `SearchTrace`, `SearchStage`, and `SearchCandidate` records. Each candidate records its configuration, status, phase, measured rounds, selection value, and failure reason. The report renders the trace in text, JSON, and HTML.

The trace is intentionally descriptive. It does not turn screening evidence into confirmation, and it does not claim that an eliminated candidate would have failed under a longer protocol.

### P3-1: Release documentation did not describe the new tradeoffs

**Severity:** Low

v0.4.1 documentation described the validation protocol and workload definitions but had no section for adaptive search, cooperative budgets, cache semantics, profitability horizons, or the new resource diagnostics.

v0.5.0 updates README, CHANGELOG, examples, report method text, and the delivery documents. The documentation states that adaptive search is conservative screening, that budgets are cooperative, that cache hits still require fresh validation, and that profitability estimates are horizon-dependent.

## Acceptance criteria

- Grid search remains the default and the v0.4.1 validation gate is unchanged.
- Adaptive search reduces exploratory work, records a search trace, and still validates the selected candidate independently.
- A budget can stop search or validation safely, preserves completed observations, and never confirms from partial evidence.
- Cache access is opt-in, local, bounded, corruption-tolerant, and never substitutes for fresh validation.
- Profitability estimates expose their horizon, assumptions, and status.
- Resource reports include effective CPU, affinity, cgroup limits, and the multiprocessing start method.
- Text, JSON schema 5, and HTML reports expose search, budget, profitability, cache, and resource state.
- The CLI exposes the new options and safe cache management.
- The full test suite and lint checks pass before release.
