## Scope

v0.5.0 adds adaptive screening, cooperative budget categories with validation reservation, profitability estimates, an opt-in local JSON recommendation cache, search traces, resource diagnostics, and schema-5 reporting. Grid search remains the default, and the v0.4.1 independent validation gate remains the confirmation authority.

The release does not change the statistical minimum, the exact one-sided paired sign test, the `minimum` and `positive` validation policies, the bootstrap interval, invalid-observation handling, or the safe fallback to the initial configuration.

## Compatibility

- Python 3.10 through 3.14.
- PyTorch 2.10 or newer.
- CPU and CUDA systems.
- Map-style datasets only.
- Windows, Linux, and macOS are supported by the code; CI covers the configured GitHub runners. The qualification evidence in this release was collected on Windows 11.
- Existing v0.4.1 Python and CLI workflows remain valid. The JSON schema advances from 4 to 5 and the benchmark protocol advances from 4.1 to 5.0, so consumers that require the old schema should pin `v0.4.1`.

## Benchmark evidence

The six-workload qualification is recorded in `docs/V0.5.0_BENCHMARK_REPORT.md`. It used protocol 5.0, adaptive search, `sustained` selection, `--rounds 2`, `--validation-rounds 10`, `--max-workers 2`, and no cache or time budget. It completed all six workloads with zero failed configurations in 546.63 s.

The qualification ran under memory pressure with worker startup around 3.1 to 3.4 seconds. Three worker-based candidates passed sustained validation but reduced amortized throughput by roughly 98%; the reports warned about the divergence, and profitability marked every workload `not_profitable`. A separate in-memory run with `amortized` selection retained `num_workers=0`. The report treats this as a metric-choice result, not as evidence that worker configurations are generally faster.

The v0.4.1 benchmark evidence remains available in `docs/V0.4.1_BENCHMARK_REPORT.md` for historical comparison. It is not a controlled baseline for v0.5.0 because adaptive search, resource diagnostics, thread caps, and memory conditions differ.

## Known limitations

- Adaptive search is deterministic screening and refinement, not full successive-halving racing. It can eliminate a candidate that would have benefited from more rounds.
- The time budget is cooperative, not a hard process timeout. A single long trial can overrun the budget.
- The cache is local and opt-in. Cached evidence is historical and must still pass current validation.
- Profitability estimates depend on the supplied horizon and observed throughput. They do not model workload drift, hardware changes, or non-linear training costs.
- A sustained-throughput confirmation can still be unprofitable or worse for the complete trial. Use `selection_metric="amortized"` for startup-sensitive workloads.
- The memory limit is sampled and advisory, not an operating-system hard limit.
- Windows worker-spawn/pagefile failures remain environment-dependent. The qualification used `OPENBLAS_NUM_THREADS=1` and `OMP_NUM_THREADS=1` to complete worker-based trials.
- macOS is not covered by CI in this release.
- PyPI publication is not part of this release.
