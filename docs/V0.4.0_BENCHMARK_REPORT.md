# APDO v0.4.0 Benchmark Report

This report records machine-specific measurements collected on 2026-11-18 with `apdo 0.4.0` (protocol 4.0). The numbers describe one Windows laptop under a specific run configuration; they are not generalized performance claims.

## Environment

| Field | Value |
| --- | --- |

| Platform | Windows 11 (10.0.26200), AMD64 |
| CPU | Intel (Family 6 Model 154), 16 logical processors |
| PyTorch | 2.14.0+cu130 |
| CUDA | 13.0 available; NVIDIA GeForce RTX 4060 Laptop GPU (8 GB) |
| System memory | 16.8 GB total; 4.5 GB available at measurement time |
| Torch threads | 12 |
| Measurement device | `cpu` for all six workloads |

## Method

All workloads ran through `benchmarks/run_workloads.py` with:

```text
--workload all --rounds 2 --validation-rounds 2 --max-workers 2
--epochs 1 --training-rounds 2
--output-directory benchmarks/results --cache-directory benchmarks/.cache
```

- Search: 2 measured rounds plus 1 discarded warmup round per configuration.
- Validation: independent paired rounds with the `minimum` policy (`min_improvement=0.05`).
- Timing profile: `standard` (whole-cycle CUDA events; CUDA is idle because measurement device is CPU).
- Selection metric: `sustained` (default).
- Comparability policy: `warn` without sample fingerprints; batch structure was compared, sample identity was not verified.
- Loader mode: `epochs=1`. Training mode: `epochs=1` in this run; training finalists still ranked by end-to-end training throughput.
- Total wall time for the six-workload run: about 6.4 minutes. Per-workload durations are listed below.

## Lifecycle observations

Lifecycle fields come from `PassMetrics` and are reported in the summaries above.

- `in-memory`, `startup-bound`, and `training` chose `num_workers=0`. Worker startup and shutdown are effectively absent, so sustained and amortized throughput stay close (ratios of about 1.15 to 1.25).
- `cpu-heavy` and `compute-bound` paid a large first-batch cost with workers enabled: first batch about 2.08 s, total trial wall about 2.43 to 2.49 s. Sustained throughput reflects the steady-state epoch; amortized throughput divides by the full trial wall and is two to three orders of magnitude lower for these single-epoch runs.
- `cpu-heavy` recorded loader cleanup of 0.342 s on the recommended configuration; `compute-bound` recorded worker shutdown of 0.337 s. These are visible in the lifecycle fields and excluded from sustained throughput but included in the trial wall.
- Iterator initialization stayed small (0.04 to 0.37 ms) compared with first-batch acquisition whenever workers started.
- Training mode counted first-batch samples in total sample accounting; the first training step remains inside the execution timer. The recommended training configuration was the initial `num_workers=0` loader after the simplicity tie-break against `num_workers=2, prefetch_factor=2, persistent_workers=True`.

## Comparability

- `in-memory`, `cpu-heavy`, and `compute-bound` ran validation or ranking with `comparability_policy=warn`. Batch structures matched in all compared paired rounds (`structural_verified=true`), but no sample fingerprint function was supplied, so sample identity was not verified and status remained `unknown` (confidence `partial`, `sufficient_for_strict=false`).
- `disk-backed`, `startup-bound`, and `training` selected the initial configuration, so independent validation was `not_needed` and no comparison result was produced.
- Strict comparability would have blocked these candidates because sample identity was not verified; the `warn` policy reported the limitation without changing the decision.

## Stability analysis

`apdo stability` was run against `examples.synthetic_dataset:create_dataset` with:

```text
--batch-size 16 --device cpu --max-batches 2 --rounds 2 --validation-rounds 2
--no-validation --max-workers 1 --runs 3 --base-seed 42
--json benchmarks/results/stability.json --html benchmarks/results/stability.html
```

| Metric | Value |
| --- | --- |
| Runs | 3/3 succeeded, 0 failed, coverage 100% |
| Confirmed gains | 0/3 (validation disabled) |
| Agreement | 100% on `num_workers=0, pin_memory=False` |
| Median throughput | 66,636 samples/s (range 61,135 to 70,621) |
| Median gain / CI | not available (no confirmed gains) |
| Comparability | `unavailable` for all runs (validation disabled) |
| Warnings | "Only 2 batches are processed per pass; results may be unstable" for each run |

Stability JSON uses schema version 1 and retains per-run recommended configuration, validation status, throughput, amortized throughput, warning counts, and failure fields. Raw batches are never stored.

## Interpretation

- Worker parallelism helped only when per-sample CPU work was large enough to amortize worker startup (`cpu-heavy`, `compute-bound`). Cheap or preloaded data preferred `num_workers=0` on this machine.
- Sustained and amortized metrics answer different questions. Sustained throughput describes steady-state execution; amortized throughput describes the complete trial including construction, startup, transitions, shutdown, and cleanup. Short single-epoch runs make the gap large.
- Two-batch stability runs are intentionally small smoke runs; their agreement and throughput spread must not be read as a general tuning recommendation.

## Reproduction

```bash
python -m pip install -e ".[dev]"
python benchmarks/run_workloads.py --workload all --rounds 2 --validation-rounds 2 --max-workers 2 --epochs 1 --training-rounds 2
python -m apdo stability --dataset examples.synthetic_dataset:create_dataset --batch-size 16 --device cpu --max-batches 2 --rounds 2 --validation-rounds 2 --no-validation --max-workers 1 --runs 3 --base-seed 42
```

Machine, library versions, background load, and thermal state affect every number in this report.
