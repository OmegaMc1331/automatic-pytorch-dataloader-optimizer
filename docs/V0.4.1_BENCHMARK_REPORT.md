# APDO v0.4.1 Benchmark Report

This report records machine-specific measurements collected on 2026-11-25 with `apdo 0.4.1` (protocol 4.1). The numbers describe one Windows laptop under one run configuration. They are not generalized performance claims, and they are not a comparison of dataset quality or model quality.

## Environment

| Component | Value |
| --- | --- |
| OS | Windows 11, 64-bit |
| Python | 3.14.5 |
| PyTorch | 2.14.0+cu130 |
| CUDA | 13.0 |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU, 8 GB |
| CPU | 16 logical processors |
| RAM | 15.7 GiB |

## v0.4.1 configuration

```bash
python benchmarks/run_workloads.py \
  --workload all \
  --device cpu \
  --rounds 2 \
  --validation-rounds 10 \
  --max-workers 2 \
  --epochs 1 \
  --loader-epochs 1 \
  --training-rounds 2 \
  --output-directory benchmarks/results \
  --cache-directory benchmarks/.cache
```

The run used protocol 4.1, the default `minimum` validation policy, the `sustained` selection metric, and the `warn` comparability policy without a sample fingerprint function. Generated data and reports were written to ignored directories under `benchmarks/.cache/` and `benchmarks/results/`.

Total wall time was 430.68 s (7.18 min). Per-workload durations include search, training where applicable, validation, and report generation.

## Validation evidence

| Workload | Valid / planned pairs | Rejected | Observed gain | 95% interval | Sign-test successes | p-value | Status |
| --- | --- | --- | --- | --- | --- | --- | --- |
| cpu-heavy | 10 / 10 | 0 | +82.74% | [+39.78%, +93.59%] | 8 / 10 | 0.0546875 | `inconclusive` |

The cpu-heavy search candidate was `num_workers=2, pin_memory=False, prefetch_factor=2, persistent_workers=False`. Search estimated +82.24% sustained throughput. Validation observed +82.74% on the median, with eight of ten pairs faster on the candidate. One pair was slower by 19.20% and another was only +64.00%, so the exact one-sided sign test returned `p = 56 / 1024 = 0.0546875`, which does not cross `alpha = 0.05`. The initial configuration was retained.

This result is intentionally reported as `inconclusive`. Rerunning until nine successes appear would be outcome-dependent analysis, not an independent confirmation. The result also demonstrates the protocol's conservatism: a large observed median and an interval entirely above zero are not sufficient without the sign test.

The candidate was not a safe general choice even though its sustained throughput was higher. Its first batch took about 2.13 s, so amortized throughput fell to roughly 253 samples/s versus 12,043 samples/s for the initial configuration. The report emitted:

> The search-selected candidate improved sustained throughput by +82.2% but reduced amortized throughput by -98.0% versus the initial configuration. Sustained and total-trial behavior diverge materially; consider selection_metric='amortized' when startup and cleanup costs matter.

This is the intended behavior: sustained selection can expose a real steady-state win, while the metric choice remains visible and validation remains a separate gate.

## Workload observations

- `in-memory`, `disk-backed`, and `startup-bound` preferred `num_workers=0`. Cheap or preloaded data did not repay worker startup on this machine.
- `compute-bound` ran a real MLP training step on cheap input and selected `num_workers=0`. With 32 batches, its baseline median was 1.31 ms of model step latency and 10.52 ms of aggregate data wait per epoch, so model compute dominated the measured trial.
- `training` also selected `num_workers=0`; its end-to-end training throughput was 26,718 samples/s.
- `cpu-heavy` shows why sustained and amortized decisions must be explicit. Worker parallelism won the steady-state epoch but lost the complete trial because of startup and shutdown.

## Comparison with v0.4.0

A fresh v0.4.0 run was executed from a detached worktree at `3705482` with the same workloads, `--rounds 2 --max-workers 2 --epochs 1 --training-rounds 2`, but `--validation-rounds 2` and the v0.4.0 workload definitions. It completed in 406.98 s. The v0.4.1 run completed in 430.68 s, about 5.8% longer.

| Workload | v0.4.0 duration | v0.4.1 duration | Change |
| --- | --- | --- | --- |
| in-memory | 62.97 s | 60.37 s | -4.1% |
| disk-backed | 64.17 s | 62.87 s | -2.0% |
| cpu-heavy | 69.81 s | 89.40 s | +28.1% |
| startup-bound | 62.82 s | 60.99 s | -2.9% |
| compute-bound | 68.25 s | 77.93 s | +14.2% |
| training | 78.96 s | 79.12 s | +0.2% |

The comparison is not controlled. v0.4.1 used ten validation rounds instead of two, and the compute-bound workload changed from a loader workload to real training. The cpu-heavy increase is dominated by eight additional validation pairs, each involving worker construction and teardown. The compute-bound increase reflects the new model step rather than a regression in loader measurement. These runs validate the release on real hardware; they do not establish a performance regression or improvement between releases.

## Stability evidence

A five-run stability check used the synthetic example dataset with twenty batches, two search rounds, ten validation rounds, and a maximum of two workers:

```bash
python -m apdo stability \
  --dataset examples.synthetic_dataset:create_dataset \
  --batch-size 16 \
  --device cpu \
  --max-batches 20 \
  --rounds 2 \
  --validation-rounds 10 \
  --max-workers 2 \
  --runs 5 \
  --base-seed 42 \
  --json benchmarks/results/stability.json \
  --html benchmarks/results/stability.html
```

All five runs succeeded and recommended `num_workers=0, pin_memory=False`, for 100% recommendation and candidate agreement. No run confirmed a gain because every run selected the initial configuration, so no validation pairs were needed. Qualification was `partial`, not `complete`, and the report emitted the expected warnings:

- Five successful runs had fewer than eight valid paired validation observations.
- No independent optimization produced a confirmed gain.
- High recommendation agreement (100.0%) was not evidence of improvement.

This is the corrected behavior: agreement is reported, but it is not presented as a confirmed speedup. The search candidate and initial configuration were identical in this workload, so the result is evidence of stable initial retention, not evidence that an optimized configuration generalizes.

## Interpretation

- The release reproduces on the recorded machine, and the six workloads produce reports with protocol 4.1 fields.
- The validation gate is conservative. A practically large sustained gain with two regressions can remain `inconclusive`.
- The `sustained` and `amortized` metrics can disagree by two orders of magnitude for worker configurations with expensive startup. Users should choose the metric that matches their workload.
- Five of six workloads selected the initial configuration, which is a valid outcome and demonstrates that the search does not force a change.
- Results are specific to this Windows machine, this PyTorch build, these workloads, and this run configuration.
