# APDO v0.5.0 Benchmark Report

This report records machine-specific measurements collected on 2026-11-28 with `apdo 0.5.0` (protocol 5.0). The numbers describe one Windows laptop under one run configuration and one period of memory pressure. They are not generalized performance claims, and they are not a comparison of dataset quality or model quality.

## Environment

| Component | Value |
| --- | --- |
| OS | Windows 11, 64-bit |
| Python | 3.14.5 |
| PyTorch | 2.14.0+cu130 |
| CUDA | 13.0 |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU, 8 GB |
| CPU | 16 logical processors |
| RAM | 15.7 GiB |
| Effective CPUs | 16 |
| Multiprocessing start method | `default` before worker initialization; Windows spawn is used when workers start |
| Cgroup limits | none reported |
| Torch threads | 1 |

The qualification process set `OPENBLAS_NUM_THREADS=1` and `OMP_NUM_THREADS=1`. Without those caps, Windows worker processes intermittently failed with `DataLoader worker ... exited unexpectedly` and `OpenBLAS error: Memory allocation still failed after 10 retries`. The capped run completed all six workloads with zero failed configurations. The machine had about 3 GB of free physical memory during the final run, and worker startup took roughly 3.1 to 3.4 seconds in worker-based trials. That startup cost is visible in the amortized and profitability results.

## v0.5.0 configuration

Each workload was run in a fresh Python process with the same arguments:

```powershell
$env:OPENBLAS_NUM_THREADS = "1"
$env:OMP_NUM_THREADS = "1"
foreach ($workload in "in-memory", "disk-backed", "cpu-heavy", "startup-bound", "compute-bound", "training") {
  python benchmarks/run_workloads.py `
    --workload $workload `
    --device cpu `
    --rounds 2 `
    --validation-rounds 10 `
    --max-workers 2 `
    --epochs 1 `
    --loader-epochs 1 `
    --training-rounds 2 `
    --search-strategy adaptive `
    --planned-epochs 50 `
    --output-directory benchmarks/results-v0.5.0-final `
    --cache-directory benchmarks/.cache
}
```

The run used protocol 5.0, the default `minimum` validation policy, the `sustained` selection metric, and the `warn` comparability policy without a sample fingerprint function. Adaptive search was enabled. The cache policy remained `off`, and no time budget was supplied. Generated data and reports were written to ignored directories under `benchmarks/.cache/` and `benchmarks/results-v0.5.0-final/`.

Total wall time was 546.63 s (9.11 min). Per-workload durations include search, training where applicable, validation, and report generation.

The `confirmed` status applies to the selected metric, which was `sustained` throughput. It does not mean the complete trial was faster. The in-memory, disk-backed, and cpu-heavy candidates all reduced amortized throughput by roughly 98% because worker startup took about 3.1 to 3.4 seconds under this run's memory pressure. The report emitted the material-divergence warning:

> The search-selected candidate improved sustained throughput by ... but reduced amortized throughput by ... versus the initial configuration. Sustained and total-trial behavior diverge materially; consider selection_metric='amortized' when startup and cleanup costs matter.

A separate in-memory run with `--selection-metric amortized` retained `num_workers=0, pin_memory=False`, recorded 35,162.7 sustained samples/s and 32,452.1 amortized samples/s, and needed no validation because the search selected the initial configuration. That run completed in 46.60 s. It demonstrates that the metric choice changes the recommendation when startup dominates.

The compute-bound result is a regression under the configured policy and retained the initial configuration. The training result had a positive interval but only eight sign-test successes, so it remained `inconclusive`; rerunning until a ninth success appeared would be outcome-dependent analysis, not independent confirmation.

## Adaptive search trace

Every workload used `search_strategy=adaptive`. The loader workloads measured six unique candidates and recorded screening plus flag-sweep stages. The training workloads measured six search candidates and three training finalists. The trace recorded selected and fastest configurations, candidate statuses, measured rounds, selection values, failures, and budget state. No candidate was skipped by budget because no budget was supplied.

Adaptive search reduced the exploratory rounds and limited the flag sweep to one worker finalist. It did not change the independent validation gate. The selected candidates still needed fresh paired validation, and the compute-bound and training workloads retained the initial configuration when validation did not confirm a gain.

## Budget, cache, and profitability

All six workloads ran with an unlimited budget and `cache_policy="off"`. The cache section therefore reported `cache disabled`, and the budget section reported `unlimited`. This run did not exercise a cache hit or a budget-truncated search; those paths are covered by `tests/test_cache.py`, `tests/test_budget.py`, and `tests/test_optimizer.py`.

Profitability was `not_profitable` for every workload. The confirmed worker candidates saved a negative amount per epoch because their first trial was much slower than the initial configuration:

| Workload | Status | Saved per epoch | Net savings over 50 epochs | Optimization cost |
| --- | --- | --- | --- | --- |
| in-memory | `not_profitable` | -3.037 s | -236.299 s | 84.427 s |
| disk-backed | `not_profitable` | -3.063 s | -243.662 s | 90.523 s |
| cpu-heavy | `not_profitable` | -3.273 s | -257.047 s | 93.399 s |
| startup-bound | `not_profitable` | 0.000 s | 0.000 s | 48.116 s |
| compute-bound | `not_profitable` | 0.000 s | 0.000 s | 122.799 s |
| training | `not_profitable` | 0.000 s | 0.000 s | 107.365 s |

The startup-bound, compute-bound, and training rows retained the initial configuration, so no gain was available. The other rows are a direct example of why sustained confirmation and profitability are separate questions.

## Workload observations

- `in-memory`, `disk-backed`, and `cpu-heavy` confirmed worker configurations on sustained throughput, but their amortized throughput collapsed under worker startup. This is a stress result, not evidence that worker configurations are generally faster on this machine.
- `startup-bound` retained `num_workers=0`; cheap data did not repay worker startup.
- `compute-bound` ran a real MLP training step on cheap input. The selected candidate was slightly slower in validation, so the initial configuration was retained.
- `training` retained `num_workers=0` after an inconclusive validation with a positive observed interval and eight of ten sign-test successes.
- The `sustained` metric can confirm a configuration that is worse for the complete trial. The report warns about the divergence, and the profitability estimate marks it `not_profitable`.

## Comparison with v0.4.1

The v0.4.1 qualification completed in 430.68 s with no failed configurations and five of six workloads retaining the initial configuration. The v0.5.0 qualification completed in 546.63 s with zero failed configurations. The comparison is not controlled:

- v0.5.0 used adaptive search, the new resource diagnostics, and the OpenBLAS/OpenMP thread caps.
- The v0.5.0 run was executed under lower free memory and much slower worker startup.
- v0.4.1 reported cpu-heavy as `inconclusive`; v0.5.0 confirmed a different worker candidate under different startup conditions.

These runs validate the release on real hardware; they do not establish a performance regression or improvement between releases.

## Interpretation

- The release reproduces on the recorded machine, and the six workloads produce schema-5 reports with search, budget, profitability, cache, and resource fields.
- Adaptive search records its decisions and keeps independent validation as the confirmation gate.
- Sustained and amortized metrics can disagree by orders of magnitude. Users should choose the metric that matches their workload, especially for one-epoch trials.
- A confirmed sustained gain is not automatically profitable. The profitability estimate can identify a recommendation that would cost more time than it saves.
- The cache and budget features are tested but were not exercised by this six-workload qualification because both were disabled.
- Results are specific to this Windows machine, this PyTorch build, these workloads, this memory pressure, and this run configuration.
