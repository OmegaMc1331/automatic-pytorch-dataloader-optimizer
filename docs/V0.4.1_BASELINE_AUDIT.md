# APDO v0.4.1 Baseline Audit

This audit records the v0.4.0 behavior that motivated the v0.4.1 reliability release. It was performed on the released `v0.4.0` tag (`3705482`) with the same source tree, test suite, and machine used for the v0.4.1 qualification.

## Environment

| Component | Value |
| --- | --- |
| OS | Windows 11, 64-bit |
| Python | 3.14.5 |
| PyTorch | 2.14.0+cu130 |
| CUDA | 13.0 |
| GPU | NVIDIA GeForce RTX 4060 Laptop GPU, 8 GB |
| CPU | 16 logical processors |
| RAM | 15.7 GiB |

## Severity legend

- **High**: can produce a wrong recommendation, a false confirmation, or misleading delivery evidence.
- **Medium**: can mislead an operator or make a report internally inconsistent.
- **Low**: documentation, diagnostics, or presentation defect without a direct decision error.

## Findings

### P1-1: Validation could confirm a gain from too little evidence

**Severity:** High

v0.4.0 accepted validation with as few as two paired observations, and it used a bootstrap interval without a sign test. A candidate could therefore be confirmed with two favorable pairs, and a single provider-side outlier could dominate the decision. The default validation count was five, but the implementation did not enforce a meaningful statistical minimum.

v0.4.1 requires at least eight valid pairs, applies an exact one-sided paired sign test at `alpha = 0.05`, and retains the configured policy's observed-median and interval conditions. A gain exactly at the threshold is counted as a failure.

Evidence: `tests/test_validation.py` covers the eight-pair minimum, exact-threshold ties, sign-test success counts, and policy decisions. `tests/test_optimizer.py` covers the incomplete-budget path.

### P1-2: Selection and reporting could use different metrics

**Severity:** High

v0.4.0 added the `amortized` selection metric, but worker finalists, training candidates, final selection, ranking, and report values were not consistently driven by the requested metric. A run could select for one behavior and display another, especially when startup or cleanup dominated.

v0.4.1 routes `sustained` and `amortized` through the same central helpers for finalist workers, training candidates, selection, ranking, JSON, text, and HTML. Regression tests use fixtures where sustained and amortized rankings differ.

Evidence: `src/apdo/metrics.py`, `tests/test_optimizer.py::test_finalist_workers_follow_the_selected_metric`, `tests/test_optimizer.py::test_training_candidates_follow_the_selected_metric`, and `tests/test_report.py`.

### P1-3: Invalid observations were replaced with zero or dropped silently

**Severity:** High

v0.4.0 treated incomplete, non-finite, or non-positive paired observations as zero gains in some paths. Zero substitution biases a median and can turn a measurement failure into a regression or a confirmation. It also hides why a pair was unusable.

v0.4.1 rejects invalid observations explicitly, records the validity reason, reports rejected observations separately, and computes statistics only from valid pairs. Invalid observations are never replaced with zeros.

Evidence: `tests/test_validation.py` covers incomplete pairs, structural mismatches, non-finite throughput, zero throughput, and rejected-observation payloads.

### P1-4: Budget-truncated validation discarded completed evidence

**Severity:** High

v0.4.0 could stop validation at a time-budget boundary and then report a result without the completed pairs, or report incomplete validation as if it were a complete protocol. The final configuration could remain safe, but the evidence was not auditable.

v0.4.1 retains every completed pair, records `planned_pairs`, `completed_pairs`, `validation_incomplete`, and the validation status `not_possible`, and never confirms a candidate from a truncated plan.

Evidence: `tests/test_optimizer.py` covers budget exhaustion with three planned pairs and preserves the observations and 100% measured improvement while refusing confirmation.

### P2-1: Stability agreement could overstate evidence

**Severity:** Medium

v0.4.0 summarized recommendation agreement and median gain without separating confirmed gains from fallback or initial-configuration choices. A run that retained the initial configuration after failed validation still counted toward agreement and could be described as stable even though no run confirmed a speedup.

v0.4.1 separates confirmed runs, fallback runs, and initial-configuration retention; reports candidate agreement alongside recommendation agreement; keeps search-candidate gains in `improvement_percent`; provides confirmed-only gain statistics; and warns when validation pairs are insufficient or no run confirmed a gain. Qualification now describes whether every successful run contributed at least eight valid validation pairs, not the strength of the evidence.

Evidence: `tests/test_stability.py::test_fallbacks_are_counted_separately_from_confirmed_runs` and `tests/test_stability.py::test_confirmed_gain_statistics_ignore_fallbacks`.

### P2-2: Startup-bound and compute-bound workloads did not measure their names

**Severity:** Medium

v0.4.0 ran the startup-bound workload for one epoch, which limited the contribution of repeated iterator and worker startup. The compute-bound workload varied loader transformations rather than running model compute and could recommend a loader configuration for a workload that was not compute-bound.

v0.4.1 runs the startup-bound loader across multiple epochs when requested and gives compute-bound a real MLP forward pass, cross-entropy loss, backward pass, and optimizer step over cheap input. The v0.4.1 benchmark report identifies the resulting behavior instead of claiming that either workload is universal.

Evidence: `benchmarks/workloads.py`, `benchmarks/run_workloads.py`, and `tests/test_workloads.py`.

### P3-1: Protocol and validation documentation were ambiguous

**Severity:** Low

v0.4.0 documentation described the bootstrap policy but not the sign test, the eight-pair minimum, invalid-pair handling, or the difference between a complete stability protocol and confirmed evidence. It also described the compute-bound workload as loader work.

v0.4.1 updates README, CHANGELOG, examples, and delivery documents to match the implemented protocol and to state what the evidence does and does not establish.

## Acceptance criteria

- A recommendation is confirmed only with at least eight valid pairs, complete validation, the policy condition, and the sign test.
- Every selection and report path honors `selection_metric`.
- Invalid validation observations are excluded and visible.
- Budget-truncated validation keeps completed observations and cannot confirm.
- Stability separates confirmed gains from fallback and initial retention.
- Startup-bound and compute-bound workloads measure the behavior they describe.
- Public defaults, API compatibility, and JSON schema version 4 remain intact; protocol moves to 4.1.
- Unit tests, real CPU benchmark runs, build checks, and CI pass before release.

## Result

All acceptance criteria are implemented in the v0.4.1 source tree and covered by the tests listed above. Real CPU evidence is recorded in `docs/V0.4.1_BENCHMARK_REPORT.md`; release checks are recorded in `docs/V0.4.1_DELIVERY.md`.
